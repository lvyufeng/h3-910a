# R147 — 用设备事件重新归因：GEMM 其实没问题，问题在 FP32 范围保护

**本轮又推翻了自己上一轮的结论。** R141/R146 说"四个 linear 一致慢 2.5–7×、GEMM 区域 7.283 s"，
那是建立在 `synchronize()` 区域计时上的；`synchronize()` 会排空**所有流**（包括权重拷贝流），
把跨流等待折进区域时间里。本轮改为**纯设备事件、forward 内零同步**（与 R143 同一套方法）。

## 结论

1. **`qkv` 1.37×、`fc1` 1.21× —— 基本是高效的。** 之前"3.35×/2.87×"是计时假象。
   也就是说**裸 GEMM 这条路没有大空间**，#6 的"GEMM 布局"基本可以放下。
2. **只有 `out_proj`（6.71×）和 `fc2`（2.45×）低效**，而这两个恰好是唯一走
   `_MiniMaxH3HalfInputFP32OutputLinearMethod` 的层。
3. GEMM 合计 in-model **4.435 s** vs 独立 **2.322 s**
   → 可回收 **2.099 s/step**；其中
   **1.665 s（79.3%）在带 guard 的两个层**，
   不带 guard 的两个层只占 0.434 s。

## 新的首要目标：FP32 范围保护的 prologue

该 guard 每次调用做：FP32 upcast 整个激活 → **整张量 `amax`** → **`float(peak)` 主机同步** →
除以 2 的幂 → 转回 FP16 → mm(FP32 out) → 乘 scale → FP32 bias 加。每步调用 **100 次**（2 层 × 50 块）。

**可能存在逐位等价的快路径**：当 `peak ≤ 32752` 时 `exponent=0`、`scale=1.0`，
此时 `FP16 → FP32 → 除 1.0 → FP16` 是**精确往返**，prologue 在数学上是恒等变换。
因此在该区间跳过 prologue 是**构造上逐位相同**——但这必须**证明并验证**，不能假设：
- 需确认 `product/1.0` 与 `product` 在 FP32 下逐位相同（是，除 1.0 精确）；
- 需确认 `.to(float16)` 对已是 FP16 的值精确（是）；
- 需确认 `result * 1.0` 精确（是）；
- 仍需处理 `peak > 32752` 的区间（保留原路径）。
- 还要验证 155 条 Half 检查与全部输出位相同。
