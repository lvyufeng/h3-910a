# R154 — stride 假设被推翻；但发现 mlp 区域有 10× 的环境性差距

## 结论先说

1. **"非连续视图导致慢 60×"的假设被否定**：连续化能省 1.59×，但两次拷贝正好吃掉全部收益，净收益 **0.001 ms**。
2. **更重要的发现**：同一套算子在 standalone 只要 **3.239 ms**，而模型里 mlp 区域
   "fc1 到 fc2 之间"记为 **33.58 ms/层**——**差约 10 倍**。所以那 34.7 ms **不是这些逐元素算子**。
3. R153b 的归因方法本身有缺陷（`median(mlp) − median(fc1) − median(fc2)` 不是可加分解），我撤回那个归因。

## 实测（单卡 npu:0，M=10448，N=7168，行 stride 14336）

| 路径 | 中位 |
|---|---|
| strided `silu` / `mul` / `silu*mul` | 1.737 / 2.103 / **3.239** ms |
| 连续 `silu` / `mul` / `silu*mul` | 1.133 / 0.903 / **2.041** ms |
| 两次拷贝 | 1.207 ms |
| **连续 + 拷贝（公平对比）** | **3.238 ms** |

strided 相对连续的算子惩罚 **1.59×**——惩罚是真的，
但 `连续+拷贝` = **3.238 ms** ≈ `strided` = **3.239 ms**，
**净收益 0.001 ms/层**。这条优化**不值得做**。

## 逐位相同（有价值的事实）

`torch.equal` = **True**，差异元素 **0** / 74891264，
max abs diff 0.0。即：连续化路径**没有任何数值风险**。
如果将来因为别的原因需要它，可以安全使用；但**现在它没有性能价值**。

## 真正的线索：10× 的环境性差距

- standalone：3.239 ms
- 模型内该区间：约 33.6 ms/层

差 10 倍，且模型里**没有 TP/USP 通信**参与这段（都在 attention 那边）。
最可能的机制是**环境**而非算术：
- 模型每层新分配约 600 MB 的 FP32 输出 + 两个 300 MB 临时量，而 offloader 正在活动；
- standalone 复用同一块缓冲，完全没有分配压力。
- 分配器压力或流等待，正好会表现成这种"算子很快、区间很慢"。

## 下一步（纯测量）

1. 把 mlp 区域改成**单一包裹 span + 内部激活 span**（真正可加的父子对），而不是三个 median 相减；
2. 若差距仍在，则查该区间内的**分配器事件**（是否反复 free/alloc 大块）与**流等待**。

## 限制

- 单卡，无 TP/USP 流量，无 offloader 活动——这正是它与模型内差异的来源；
- 本轮未改模型、未装候选。
