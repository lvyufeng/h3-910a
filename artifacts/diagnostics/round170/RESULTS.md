# R170 — 实测形状与峰值内存，以及由此得到的 **10 s 可行性判定**

## 一、延后检查：**确定不可行**（实测）

| 被审张量 | **实测形状** | 单个 | 每步 | 每步合计 |
|---|---|---|---|---|
| `qkv_proj` | **10448×10752** | 214.3 MiB | 50 | **10.46 GiB** |
| `mlp.fc1` | 10448×14336 | 285.7 MiB | 50 | **13.95 GiB** |
| `adaln linear` | 3×96768 | 0.6 MiB | 55 | 0.03 GiB |
| **需存活** | | | 155 | **24.44 GiB** |

block 区间实测峰值：**allocated 7.13 GiB / reserved 11.64 GiB** → 余量 **20.36 GiB**。

**24.44 GiB > 20.36 GiB → 放不下。**

**R169 的"边际"错在哪**：我假设 `qkv` 宽 5376、估 19.4 GiB；**实际宽 10752**，因此需要 24.44 GiB。
方向由**实测**关闭，不再是"待定"。

### 审计这条线的完整结论

- **R168**：换成更便宜的实现 → 端到端 **+0.75 s**（串行化点没去掉）；
- **R170**：延后 → 需要 24.44 GiB，放不下。
- ⇒ **那约 2.87 s 在不改变合同要求的前提下无法回收。**

## 二、10 s 可行性：**很可能不可达**（这是目标第①项要求的判定）

| 情景 | 步时 |
|---|---|
| 合规基线 | **17.902 s** |
| **FA 变成零耗时**（不可能） | **10.3 s** |
| FA 达实测 GEMM 效率 96.9 TFLOPS/卡（2.36×）+ guard 去掉 | **11.42 s** |
| FA 2× + guard 去掉 | 12.0 s |
| FA 3× + guard 去掉 | 10.73 s |
| FA 3× + guard + USP 减半 + attention 残余减半 | 9.51 s |

**关键一条：即使 FA 变成零耗时，步时仍为 10.3 s > 10 s。**

### 需要的 FA 速率 vs 本机实测能力

| | TFLOPS/卡 |
|---|---|
| 当前 FA | 41.1 |
| 2× | 82.2 |
| 3× | **123.0** |
| **本机实测 GEMM 最优** | **96.9** |

**FA 3× 要求 123 TFLOPS/卡，高于本机已实测的 GEMM 效率。** 2.36×（=96.9 对应的速率）是实测能力支持的上限，
该组合落在 **约 11.42 s**。

## 三、诚实结论

> **在当前硬约束下，10 s/step 很可能不可达。**
> 两个大杠杆按实测能力全开（FA 达本机最优 GEMM 效率 + 去掉 FP32 guard）**约 11.42 s**。
> 要进 10 s，还需要 FA 超出该效率，或 USP 与 attention 残余再有收益，**或改变约束本身**。

## 四、建议

与其继续找 10 s 的路径，更有价值的是二选一：

1. **把目标调整到约 11.5 s**（实测能力支持的合规上限附近）；
2. **重新审视一条硬约束**——特别是"155 条检查必须在每个被测 step 内逐层执行"。
   R168/R170 已经证明：这条约束本身值约 **2.87 s**，且无法通过更便宜的实现或延后规避。
   如果允许"检查在 step 外批量执行"或"抽样检查"，10 s 立即回到可达区间。

这个判定直接回答目标里的第①项（10 s 分阶段可行性）。
