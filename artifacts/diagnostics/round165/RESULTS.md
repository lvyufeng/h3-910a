# R165 — 为什么快速检查必然失败：**这台设备的 FP16 浮点判据不可靠**

## 起因

R164 发现快速检查在含 NaN 的张量上**漏检**。本轮查设备行为本身，45 个用例（形状 × 位置 × 种类）。

## 结果

| 判据 | 与原生位模式计数不一致的次数 |
|---|---|
| `isnan().sum() + isinf().sum()` | **10 / 45** |
| `x != x`（经典 NaN 判据） | **30 / 45** |

最严重的观察：

- 一个"全零 + 单个 NaN"的张量，`isnan().any()` = **False**、`isfinite().all()` = **True**
- 同一张量 `x != x` 计数 = **0**，经典判据同样失效
- 该张量 `max()` 返回 **65504.0**（FP16 最大有限值），而不是 NaN

## 根因：仓库里早就写明了

`npu_half_nan_compat124.py`：

> "CANN lacks NanToNum here for both FP16 and FP32. ... Classify NPU FP16/FP32 bit patterns
> **without unreliable float predicates**."

**这正是那个辅助函数存在的理由。** 我 R163/R164 的"快速版"建立在代码**明令避免**的判据上，
所以它**在构造上就不成立**——R164 的漏检由此得到解释。

## 可救的方向（仍用位模式，但更便宜）

保留位模式（正确性必需），但把实现压便宜：

| 现状 | 可改 |
|---|---|
| `.view(int16).to(int32)` **扩张到 int32**（流量翻倍） | 直接在 **int16** 上做 |
| 物化 **3 个**全尺寸 mask（nan / +inf / -inf） | 由幅度场一次判定：`magnitude >= 0x7c00` 同时覆盖 NaN 与 Inf |
| 饱和：`(x.abs()==65504).sum()` | `magnitude == 0x7bff`（65504 的位模式） |

**可省掉 int32 扩张与 2 个全尺寸 mask。** 预期显著低于现在每次 24.25 ms，具体需实测。

## 必须先通过的双重验证

1. R164 的对抗套件；
2. R163 的 465 次真实数据比对。

## 更正链（三轮）

1. **R163**：在"坏值计数全为 0"的真实数据上宣称"已证明等价"——过强；
2. **R164**：对抗测试推翻它；
3. **R165**：解释了根因——**该设备 FP16 浮点判据不可靠**。
