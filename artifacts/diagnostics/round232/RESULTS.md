# R232 — host 墙钟 vs 设备 span：同步点让 host 落后，剩下 3.43 s 的机制找到入口

## 一、目的

R231 归属后仍有 **3.43 s/step** 未解释（`attn` 1.23 + `mlp` 1.74 + `block` 0.46）。
R231 的假设是“host 派发造成设备气泡”。本轮在**同一批模块钩子里同时记录 host `perf_counter`
与设备事件**，直接对比两者。

**步时不变性**：17.9465 s vs 基准 17.928 s，**+0.019 s**（远优于 R231 的 +0.092 s），
8 rank 全部完成，数据可采信。

## 三、判读：两条完全不同的性质

1. **计算主体是设备侧、派发极快**：`qkv` 0.24 ms、`fc1` 0.23 ms、`packed_attention` 4.16 ms
   的 host 墙钟只占其设备 span 的 1.4%–2.4%。⇒ 派发不是瓶颈，FA/USP/GEMM 的时间是真的在算。
2. **同步点让 host 长时间阻塞**：
   - `out_proj`：设备只用 18.2 ms，host 却阻塞 **179.6 ms**。`out_proj` 正是走
     `_MiniMaxH3HalfInputFP32OutputLinearMethod` 的受保护层，其 `float(product.abs().amax())`
     是 **host 同步点**；host 一路异步派发跑在设备前面，撞到这个同步点后被排空的队列罚站。
   - `adaln_proj`：设备 1.9 ms、host 27.0 ms。它挂着第 155 条 Half 检查（strict 模式
     `int(bad)`/`int(boundary)` 两次 host 同步），同样把 host 按住。
3. **`fc2` 只有 7.9 ms host**：因为它前面的 `out_proj`/`adaln` 同步已经把队列排空，
   轮到它时队列很短 —— 这解释了为什么 R230 里把 155 条检查切到 `deferred` 只省 0.036 s：
   **罚站的主因不是检查，而是 guard 的同步**（100 次/步，`out_proj`+`fc2` 各 50）。

## 四、新假设 H3

> 每步 100 次受保护层 host 同步（外加 155 条检查的同步）让 host 反复落后于设备；
> 同步后 host 需要“追赶”派发，追赶期间设备可能短暂空转。这类空转在设备事件 span 里
> 表现为**父区间减去子区间的未归属时间**（`attn` 26.7 ms、`mlp` 34.9 ms、`block` 9.2 ms）。

R228/R229/R230 已排除的（搬运等待、allocator、检查同步本身）不与之冲突：
H3 的主张是**同步点造成的流水线排空与追赶**，不是搬运或分配。

**验证方法（R233，仅测量）**：同一步内 A/B
- A：部署 guard（含 `float(peak)` host 同步）
- B：设备侧算 scale 的无同步 guard（R221 已证明在 scale==1 分支上与其逐位相同：
  112,336,896 word、差异 0）

对比步时与输出逐位一致性。若 B 明显更快且输出逐位相同 ⇒ H3 成立，且给出一条
**不改数值、只去除 host 同步**的候选路径（仍需用户对“精度保护路径改动”作数值决定）。

## 五、合规与限制

- 未改数学/dtype/块数/offload/调度；未安装候选；FA trim 仍 OFF；未下载/回传张量。
- host 墙钟是**单进程视角**，8 rank 共享 192 核，可能存在 CPU 争用；但 `qkv`/`fc1` 的
  0.2 ms 说明争用不足以解释 179.6 ms，主因是同步点。
- 尚未测 B 变体的步时；H3 在 R233 之前只是假设。
