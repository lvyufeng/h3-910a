# R234 — 否证 host 派发与分配阻塞；并发现此前模块 span 只采了最后一块（方法学缺陷）

## 一、两个免权重微基准

### A. 单 op 派发成本（`dispatch_cost234.py`）

设备空闲时，纯异步入队 `x.add_(y)`，按尺寸测 host 每次入队耗时与设备耗时：

| 形状 | 元素 | host 派发 ms/op | 设备 ms/op | host/设备 |
|---|---|---|---|---|
| 64×64 | 4,096 | **0.0134** | 0.0173 | 0.77× |
| 1024 | 1,024 | 0.0129 | 0.0178 | 0.72× |
| 224×128 | 28,672 | 0.0132 | 0.0178 | 0.74× |
| 1024×1024 | 1.05 M | 0.0134 | 0.0170 | 0.79× |
| 2048×4096 | 8.39 M | 0.0133 | 0.0203 | 0.65× |
| 10448×3584 | 37.4 M | 0.0138 | 0.1933 | 0.07× |

- host 派发速率 **约 7.5 万 op/s（0.013 ms/op）**，与张量大小无关。
- 要解释 `attn` 26.7 ms / `mlp` 34.9 ms 的缺口，需要 **约 2000–2700 个未计时 op**，
  而这两个区域的实际 op 数在 10–40 量级。⇒ **host 派发假设否证。**

### B. 大块分配是否在设备积压时阻塞 host（`alloc_blocking234.py`）

先排队 2000 个 `add_`（设备侧积压 **40.509 ms**），再分配 300 MB FP32（= 一次 `gate.float()` 的规模）：

| 条件 | 分配 host 墙钟 |
|---|---|
| 设备空闲 | 0.0155 ms |
| 设备积压 40.5 ms | **0.0365 ms**（+0.021 ms） |

⇒ 分配**不会**等待设备积压，allocator 没有在分配时同步。**分配阻塞假设否证。**

## 二、方法学缺陷（自查，必须记录）

复查探针代码发现：R226/R231/R232 的模块级钩子把事件存在
`_STATE["pending"][label]` 的**单槽**里（`["start"]=event`、`["end"]=event` 覆盖写），
因此**每个标签只留下最后一次调用的样本**（回执里 `calls=1` 就是证据），而我把它按 ×50 外推成每步值。

- 可支持的部分：`block` 单样本 346 ms ×50 = 17.3 s ≈ 步时 17.95 s，比例自洽；
  且 R226 的 `block/attn/mlp` 与 R231、R232 三次独立运行几乎相同（345.8–346.4 / 243.1–243.5 / 87.9–88.7），
  说明“最后一块”代表性与稳定性尚可。
- **不可支持的部分**：把单样本差额（`attn` 26.7、`mlp` 34.9、`block` 9.2 ms）当成精确的每步量，
  并据此推断 3.43 s/step 的构成。**这些数字只有单样本精度，之前的“3.43 s”应视为数量级估计而非精确值。**

## 三、结论

1. 六个候选机制现已全部否证：权重等待（R228）、allocator 拷贝争用（R229）、
   审计同步（R230）、guard 同步（R233）、host 派发（R234A）、分配阻塞（R234B）。
2. 未归属量的精确值**尚未可靠测出**，因为模块 span 只有单样本。下一轮必须先修探针：
   把每个标签的样本**追加成列表**（R226 的 `rope`/`packed` 已经这样做，回执里 `calls=200/104` 可证），
   再按 50 块取中位与分布，才能回答“3.43 s 是否真实存在、分布是否均匀”。
3. 在精确分解之前，**不应再提出任何以“省这 3.43 s”为前提的候选**。
