# R143／R144 — staging 时序 + 真实形状（并更正 R142 的错误）

两个纯测量实验合在一轮：R143 用 copy-stream / compute-stream device 事件对齐每层权重到达时刻；
R144 记录四个 linear 与 FA 在模型里**实际看到**的 tensor 形状。两者都未改数学、未改生命周期。

## 1. 更正 R142（重要）

R142 我在微基准里用错了三个形状，导致对"谁慢"的判断失真：

| case | R142 实际用的 MKN | 真实 MKN（R144 实测） | FLOP 比 |
|---|---|---|---|
| `qkv_proj` | (10448, 5376, **7168**) | (10448, 5376, **10752**) | ×1.50 |
| `mlp.fc1` | (10448, 5376, **28672**) | (10448, 5376, **14336**) | ×0.50 |
| `attn.out_proj` | (10448, **7168**, 5376) | (10448, **3584**, 5376) | ×0.50 |
| `mlp.fc2` | (10448, **14336**, 5376) | (10448, **7168**, 5376) | ×0.50 |

因此 R142 里"qkv 只有 3.1% peak、是异常点"这个说法**不成立**——那是我把 N 算小了 1.5 倍的产物。
真实的 `qkv_proj`（FP16 进 FP16 出）在隔离态并不差。

## 2. 真实形状（R144，8 rank 全部完成）

| 模块 | 输入 | 权重 | 输入 dtype | 输出 dtype |
|---|---|---|---|---|
| `attn.qkv_proj` | [10448, 5376] | [10752, 5376] | float16 | float16 |
| `attn.out_proj` | [10448, 3584] | [5376, 3584] | float16 | **float32** |
| `mlp.fc1` | [10448, 5376] | [14336, 5376] | float16 | **float32** |
| `mlp.fc2` | [10448, 7168] | [5376, 7168] | **float32** | float32 |
| `FA` | q/k/v [1, 7, 41792, 128] | — | float16 | — |

关键：**FA 作用在完整序列 41792 上，每 rank 只有 7 个 head** → USP 切的是 head 而不是 token。
`n_pad=23`。这也解释了为什么 FA 的 FLOPs 很大。

`fc1`/`out_proj`/`fc2` 全都输出 FP32，这解释了它们隔离态只有 **11–23% of FP16 peak**：
它们的天花板是 FP32 路径，不是 FP16 peak。

## 3. 按真实形状重算的 in-model vs 隔离态

> 隔离态数字是按 FLOP 比从 R142 实测**换算**的估计值（同一 kernel、不同工作量），
> 不是直接测量；下一轮会用真实形状重测以给出实测值。

| 层 | 真实 MKN | 隔离态（换算） | in-model | 差距 | 隔离态达成率 |
|---|---|---|---|---|---|
| `qkv_proj_resident` | [10448, 5376, 10752] | 11.2 ms | 41.74 ms | **3.73×** | 107.8 TF (34.8%) |
| `mlp_fc1_resident` | [10448, 5376, 14336] | 14.88 ms | 54.6 ms | **3.67×** | 108.3 TF (34.9%) |
| `attn_out_proj_resident_fp32out` | [10448, 3584, 5376] | 5.88 ms | 19.02 ms | **3.23×** | 68.4 TF (22.1%) |
| `mlp_fc2_resident_fp32out` | [10448, 7168, 5376] | 11.36 ms | 30.3 ms | **2.67×** | 70.9 TF (22.9%) |

**四个 linear 一致地慢 2.67–3.73×**（而非 R142 说的"只有 qkv 异常"）。
若 in-model 达到隔离态速率，GEMM 区域 **7.283 s → 2.166 s，
潜在回收 ≈5.117 s/step**（含估计误差，且 in-model 数字含区域 hook 的同步开销）。

## 4. staging 时序：拷贝**没有** stall（R143）

| 指标 | 值 |
|---|---|
| 基线步时（只有本探针，无区域 hook） | **18.076 s**（8 rank 全部一致） |
| 每 block 耗时 | 348.7 ms（50 块合计 17.44 s） |
| 每 block 权重拷贝（copy-stream span） | 59.3 ms（合计 2.94 s/step） |
| 拷贝完成时刻（相对当前 block 开始） | +315.3 ms |
| 到**下一个** block 开始的余量 | 中位 **33.8 ms**，最小 21.4 ms |

结论：**权重是"刚好赶上"而非"在等"**——拷贝在下一个块开始前 22–34 ms 完成，全程与计算并行。
所以 #4 的候选方向**不是"提前预取"**（没有富余可抢），也印证 R142 的 3.7 s 不能简单归因于拷贝停顿。

顺带更正 R140 的一个数字：那轮说的 prefetch 7.62 s 是 201 次调用（含非 block 路径），
真正的 block 级权重拷贝合计是 **2.94 s/step**，每块 59 ms，
约为纯带宽下限（0.646 GB ÷ 21.8 GB/s = 29.6 ms）的 2 倍。

## 5. 那么 ~3× 的差距来自哪

已排除：拷贝停顿（有 22–34 ms 余量）。
待测（下一轮，仍是纯测量）：
1. **block pre-hook 内的权重物化**（pinned master → device tensor 的 cast/copy 在 compute stream 上），
   它发生在 block forward 之前，因此不在 attn/mlp 子区间里，可能正是那 3× 的来源；
2. 每 op 的 dispatch 开销（M=10448 时 op 变小，固定开销占比升高）；
3. FP32 输出路径的实际执行效率（需要 profiler 而不是计时）。

## 限制

- 隔离态为 FLOP 比换算的估计值，未在真实形状上直接测量（下一轮补）。
- in-model 数字来自 R141（含 5 个额外同步 hook 的 ~0.9 s 开销），比例结论稳健但绝对值偏高。
- 310 TF 为数量级假设；本轮未改数学、未安装候选，**不构成任何数值批准**。
