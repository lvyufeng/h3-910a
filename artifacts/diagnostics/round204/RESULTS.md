# R204 — encoder <2 s 的**完整可行解**：载入 device 一次、释放 host 副本

## 一、先否掉 R203 的解法 2（vision 塔排除）

R203 提议"纯文本下不需要 vision 塔，排除它可降低 pinned 需求"。本轮算了确切参数量：

| 部分 | 参数量 | bf16 体积 |
|---|---|---|
| **text 塔**（64 层，hidden 5120，intermediate 25600） | **31.21 B** | 62.4 GB |
| embedding（151936 × 5120） | 0.778 B | 1.56 GB |
| **text 合计** | **31.98 B** | **64.0 GB** |
| **vision 塔**（27 层，hidden 1152，intermediate 4304） | **0.411 B** | **0.82 GB** |
| patch embed | 0.0009 B | 0.002 GB |

**⇒ vision 只占 0.82 GB，而缺口是 30.7 GB。解法 2 只能填 2.7%，作废。**

（顺带核对：text+vision = 64.8 GB vs 目录 63 GB，差 2.8%，属 bf16/对齐误差，**模型核对通过**。）

## 二、关键转向：**不需要两者同时 pinned**

我前一轮把"DiT 和 encoder 都要 pinned"当成了前提。**但这个前提不必要。**

encoder 的 host 副本存在的唯一理由是"作为上卡的源"。**一旦 encoder 已在 device 上，
host 副本就可以释放**，pinned 需求立刻只剩 DiT。

## 三、两种排布的内存核算

| 项 | 方案 A（朴素：两者同时 pinned） | **方案 B（encoder 上卡后释放 host 副本）** |
|---|---|---|
| pinned 需求 | 125 GB = **116.4 GiB** | **62 GB = 57.7 GiB** |
| pinned 上限 | 94.3 GiB | 94.3 GiB |
| **pinned 判定** | ❌ **差 22.2 GiB** | ✅ **余 36.5 GiB** |
| device（encoder 阶段） | — | encoder 7.33 + DiT 流式峰值 11.64 = **18.97 GiB** |
| device 上限 | — | 32 GiB |
| **device 判定** | — | ✅ **余 13.03 GiB** |

**⇒ 方案 B 两个预算都通过，且都有充裕余量。**

## 四、代价与收益

| 项 | 值 |
|---|---|
| 一次性代价 | 63 GB / 20 GB/s = **3.15 s**，但**每进程一次**（不是每请求） |
| 收益 | 每请求的 encoder 从 3.14 s → **纯算力 ≈0.5 s** |
| 目标 | **<2 s** |
| 判定 | ✅ **大幅达标** |
| 是否改数学 | **否**（只改权重驻留时机，计算本身不变） |

前提是进程处理**多个请求**时能摊薄这 3.15 s。若每请求都启一个新进程，则回到 3.15 s/请求
——**这一点需要确认部署方式**（benchmark 与线上服务通常是常驻进程，应可摊薄）。

## 五、这条路的完整因果链

```
encoder 时间 99% 是 63 GB 搬运（算力只 0.17 s）
    ⇒ 每次载入则 3.15 s 是硬下限（<2 s 物理不可能）
    ⇒ 唯一出路是常驻
    ⇒ 常驻需 device 7.33 GiB/rank，实测 DiT 峰值 11.64 GiB，合计 18.97 < 32 ✅
    ⇒ 但 pinned 不能同时容纳两者的 host 副本（116.4 > 94.3 GiB）
    ⇒ 解法：encoder 上卡后释放 host 副本 ⇒ pinned 只剩 DiT 57.7 GiB ✅
    ⇒ 每请求 encoder ≈0.5 s ⇒ <2 s 达成
```

**每一步都有实测或算术支撑，没有跳跃。**

## 六、诚实边界

1. **"释放 encoder host 副本"是否被现有代码允许，未验证。**
   当前实现是 `load_to_device()` / `offload_to_cpu()` 成对调用——
   要改成"上卡后不卸载"，且让 host 副本可回收（否则 pinned 仍占着）。
2. **DiT 的 62 GB pinned masters 是否全程常驻**，R126 只提到 "immutable pinned masters"，
   没有明确其生命周期。若 DiT 也是分块 pin，pinned 需求更低，方案更宽松。
3. **NUMA 隐患仍在**：8 个 NUMA 节点，pinned 内存跨节点会降低 H2D 带宽，
   而 R198 测 20 GB/s 时未记录 NUMA 布局。
4. **部署方式**：3.15 s 一次性代价能否摊薄，取决于进程是否常驻、处理多少请求。

## 七、合规

只读配置文件 + 本地算术；**本轮未占机器**；未加载权重；未改模型数学。
