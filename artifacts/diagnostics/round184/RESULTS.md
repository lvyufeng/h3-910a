# R184 — 阶段 A 集成测量：**2.566 s/步**，且不重蹈 R168

## 一、测量方法（这就是关键）

R168 的教训是"设备时间不能预测步时"——所以本轮**从 Python 侧**测量完整每层代价，
**包含 strict 审计的两次主机同步**，而不是只看设备事件。

- **原生路径**：完全照 `matrix_safety126._hook` strict 模式（`ieee_nonfinite_masks` +
  `(nan|posinf|neginf).sum()` + `(value.abs()==65504).sum()` + 两次 `int()` 强制同步）
- **内核路径**：一次 `h3_max_mag_bits()` ctypes 调用（内部 1 次 op launch + 1 次流同步）

为了能从 Python 调，把算子包了一层 C ABI 共享库（`libh3fast184.so`，13 KB）。

## 二、结果

| 张量 | 大小 | 原生/层 | 内核/层 | 倍数 | 判定一致 |

| 口径 | 每步 |

### 交叉验证：口径可信

R162 独立测得审计开销 **2.87 s**，本轮原生路径测出 **2.764 s**——两者几乎一致。
说明这个"含同步的每层测量"确实复现了真实审计代价，不是纸上推算。

## 三、为什么这次不重蹈 R168（那次更便宜反而 +0.75 s）

R168 的替换实现是"换算法但保留每层 5–6 个设备算子 + 多次同步"，
**串行化点和算术都没消**，所以端到端更差。

本轮的差别是**每层只剩 1 次 op launch + 1 次同步**：

- 原生每层要物化约 8–10 个全尺寸临时张量
  （`format_cast` 拷贝、`int16→int32` 加宽 2×、3 个 bool mask、`abs`、`eq`、2 次 `sum`）
- 内核每层只读一遍原张量（24.44 GiB/步 的数据，一趟扫完）

**14× 的每层加速是在含同步的情况下测到的**，所以串行化成本也被一起压下去了——
这正是 R168 缺的那一步。

## 四、判定等价

三个真实形状上 `native_verdict == fast_verdict` 全部一致（`all_verdicts_agree: true`）。
加上 R183 的 15/15 对抗用例（含 `nan_and_saturation`、`inf_and_saturation`、`many_bad`），
判定等价性有充分证据。

## 五、这属于需要用户决定的变更
