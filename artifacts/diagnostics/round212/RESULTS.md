## 一、上轮为什么失败

R211b 报 `sequence length must be a positive multiple of 16`，连 seq=4096 也报。
本轮读了 `fa910a.py` 的签名，找到原因：

```python
def flash_attention_910a(q, k, v, ...):
    ...
    b, h, source_n, d = q.shape            # ← 布局是 (B, H, N, D)
```

我传的是 `(1, seq, heads, hd)` = `(1, 41792, 7, 128)`，
于是它把 **`h=41792`、`source_n=7`** 读进去，`7 % 16 ≠ 0` ⇒ 报错。

**修正为 `(1, 7, 41792, 128)`，与 R159 的 per-rank 真实形状一致。**

## 三、结论闭环

**现在三层全部否证：**

| 层 | 结论 | 来源 |
|---|---|---|
| **集合通信**（HCCL all-reduce，8 rank，3 种真实宽度） | **逐位可重复** | R210 |
| **单算子**（matmul 4 个真实 GEMM 形状 / sum / max / RMSNorm / add / softmax） | **逐位可重复** | R211 |
| **FA 内核**（含 41.5% 单步占比的真实形状） | **逐位可重复** | **R212** |
| —— 而 —— | | |
| **整个 DiT 50 块** | **relRMS 0.026% 差异** | R128 |

**⇒ 数学本身、通信本身、最大算子全部确定。差异只能来自"把算子组合起来的那一层"。**

## 四、候选收窄到 #4 的领域

| 候选 | 与现有证据的吻合度 |
|---|---|
| **权重 offload/prefetch 的异步拷贝与计算竞争** | **最高** —— 逐块 offload 每步搬 32.3 GB，若 prefetch 的下一块覆盖了正在算的块，就会产生这种非位同 |
| 多 stream 交错 | 高（单算子测试都是单流） |
| allocator 复用/地址相关 tiling | 中（tiling 已证确定，但地址可能影响） |
| collective 与计算交错顺序 | 中（HCCL 确定，但交错可能不同） |

## 五、这对 #4 的意义：从"被阻塞"变成"被指向"

**#15 与 #4 的关系被重新理解：**

- 旧理解：`#15（非位同） → 阻塞 → #4（prefetch 生命周期）`
- **新理解：三层否证之后，#15 的差异最可能就出在 #4 所管的 prefetch/拷贝机制里。
  两者是同一问题的两面，#4 的手段正是解决 #15 的手段。**

**⇒ #4 的实施依据从"猜测"变成"已知这里是唯一剩下的可疑层"。**

这也意味着 **#15 的进一步定位应该直接做"prefetch 开/关下的重复性对比"**：
- prefetch 关闭 + 逐块同步搬运 → 若逐位可重复，则**确认 prefetch 是根因**；
- 这同时给出了 #4 的安全实现边界。

## 六、诚实边界

- 单算子与 FA 的测试都是**单卡单流**，测不出多卡/多流交错的问题。
  这既是第 3 节推论的基础，也是它的局限 —— 真实路径是 TP2+USP4、多流、逐块 offload。
- 4–10 次重复对极低频抖动可能不够（真实 DiT 的 0.026% 是稳定的，所以应属高频）。
- 我**没有**验证"地址变化是否改变 matmul tiling"（allocator 候选）。
