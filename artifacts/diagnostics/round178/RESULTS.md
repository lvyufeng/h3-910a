# R178 — 阶段 A 的价值有了实测支撑：**一趟归约 = 0.351 s/步**（当前审计 2.87 s）

## 为什么用代理测量

阶段 A 的价值只取决于"对同样数据做一趟归约要多久"。不需要自定义算子就能测这个：
`torch.amax(x, dim=all)` 就是单趟归约，读的字节数和一个手写统计内核完全相同。

（注：扁平 `torch.amax(x)` 会触发 `ReduceMax` 的
`aclrtAllocatorGetByStream failed` + "Output requires a 299565088 buffer, but 64 aligned buffer is allocated"，
与 R148 遇到的是同一类问题；改用带 `dim` 的归约即正常。）

## 结果（npu:0，fp16，warmup 3 / repeats 10，中位）

| 张量 | 大小 | 单次 | 有效带宽 | 每步次数 | 每步合计 |
|---|---|---|---|---|---|
| `mlp.fc1` | 285.7 MiB | **3.905 ms** | 76.7 GB/s | 50 | 195.2 ms |
| `qkv_proj` | 214.3 MiB | **2.947 ms** | 76.2 GB/s | 50 | 147.4 ms |
| `adaln_linear` | 0.6 MiB | 0.146 ms | 4.0 GB/s | 55 | 8.1 ms |
| **合计** | **24.45 GiB/步** | | | 155 | **350.7 ms = 0.351 s** |

| 口径 | 每步 |
|---|---|
| 当前审计（R162 实测） | **2.87 s** |
| 一趟归约（本轮实测） | **0.351 s** |
| **隐含节省** | **2.519 s** |

**判定：stage A remains worth pursuing: a single pass is much cheaper than the current audit**

## 三个值得注意的点

1. **有效带宽只有约 76 GB/s**，远低于 910B HBM 峰值。这说明这个代理测的是"简单归约"的下限表现，
   一个真正并行良好的内核**可能更快**——所以 0.351 s 偏保守，节省可能 >2.52 s。
2. **`adaln` 只有 0.6 MiB 却要 0.146 ms（4 GB/s）**：小张量完全被启动开销支配。
   这部分（8.1 ms/步）没有优化空间，与"每次调用固定开销"的判断一致。
3. 当前审计比一趟归约慢约 **8 倍**（2.87 / 0.351）。这是对它实现的量化定性。

## 对 10 s 规划的影响

R171 的上界计算里，审计按"0 收益、不可回收"计。本轮把前提改了：

| 组合 | 步时 |
|---|---|
| 现状（合同口径） | 17.90 s |
| + 阶段 A（实测上界 −2.52 s） | **≈15.4 s** |
| + guard（−1.67 s） | ≈13.7 s |
| + FA 达本机实测 GEMM 效率（−4.38 s） | **≈9.3 s** |

**三阶段全成，10 s 才可达。** 阶段 A 是其中最容易验证、且单独就值 2.5 s 的一步。

## 边界（必须写清）

- 这是**代理测量**，不是内核实测：证明"一趟归约只需 0.351 s"，**不证明**我的内核能达到。
- 统计内核还要多做位模式比较（`magnitude >= 0x7c00`、`== 0x7bff`），可能比纯 amax 慢一些。
- 因此阶段 A 的**真实**收益在 2.5 s 附近，需以实际内核计时为准。
