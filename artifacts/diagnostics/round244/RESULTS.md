# R244 — 第四次尝试测等待仍失败；但由此确认了**插桩扰动的真正规律**

## 一、结果

包装 `layerwise_backend.clear_block_storage`（正确定位到该模块命名空间里的名字），
每块记录一个 compute 流事件与 `ready_event` 配对：

- **`ready_event.elapsed_time(now)` 抛 `RuntimeError`，8 rank 样本数全为 0**
  ⇒ 跨流事件（copy 流事件 vs compute 流事件）的 `elapsed_time` 在本栈上不被支持，
  这条配对方案不可用。
- **步时 18.4981 s（+0.570 s）** ⇒ 远超 ±0.1 阈值，**本轮计时数据作废**。

## 二、四次尝试的统一解释（本轮真正的收获）

| 轮次 | 插桩方式 | 步时偏差 |
|---|---|---|
| R235 | 子模块 `register_forward_(pre_)hook`（约 26 个事件/块） | **+0.062 s** |
| R240 | 子模块钩子 + `apply` 包装 | **−0.004 s** |
| R243 | block 级前置钩子 | **+0.531 s** |
| R244 | 包装 `clear_block_storage`（1 事件/块） | **+0.570 s** |

对照可见：**扰动大小与事件数无关**（R235 有 26 个事件/块却几乎零扰动，R244 只有 1 个事件/块却 +0.57 s），
而与**插桩位置是否处于 `torch.compile` 捕获边界**强相关：

- 子模块的 `register_forward_(pre_)hook` 是 PyTorch 官方钩子，编译图会正确跨越它 ⇒ 几乎不扰动；
- 替换 `forward`（R236/R237）、包装 block 级钩子（R243）、包装被 `@torch.compiler.disable`
  修饰的 offloader 函数（R244）都会**打断块的编译/图捕获**，导致每块多 ~11 ms 的重捕获或调度开销。

**结论（第四条方法学规则）**：在本栈上，只有**子模块 `register_forward_(pre_)hook`** 是编译安全、
可用于计时的插桩方式；任何其它形式的包装/替换都会引入 ≥0.5 s/step 的伪影。

## 三、因此：3.457 s 的残余缺口已不可能用现有手段进一步归因

- 可用的唯一工具（子模块钩子）已经在 R235 用尽：`attn` 差 25.0、`mlp` 差 34.8 ms/块，
  子项本身经 R240 两种方法交叉验证无低估；
- 想再往下的每一条路（block 级钩子 / 包装 offloader / 替换 forward）都被证明会引入更大伪影；
- 跨流事件配对在本栈不可用（R244，`RuntimeError`）。

⇒ 结论应当如实标注为：**残余 ~3.4 s/step 在当前可用的零扰动观测手段下不可再分解**，
它可能是父区间内的真实设备工作、也可能是钩子事件对本身的结构性开销；
不应再基于“它是什么”提出候选。

## 四、对目标的战略判断（写给用户）

已可靠测得的每步构成（多种方法交叉验证）：

| 区段 | s/step | 依据 |
|---|---|---|
| FA + USP（packed attention） | **8.85** | R235/R237 一致（176.9 ms/块） |
| 四个 linear（qkv/out_proj/fc1/fc2） | **4.44** | 17.07+18.22+23.4+30.05，R240 交叉验证 |
| q/k norm + rope + adaln + norms + 元素链 | ~0.9 | R235 |
| 残余（本页第三节） | ~3.4 | 不可再分解 |

- 四个 linear 的**独立 mm 下限**（R238 实测：12.48+2.71+19.04+11.69 = 45.9 ms/块 = 2.30 s/step）
  加 TP all-reduce 1.22 s ⇒ 约 **3.5 s/step 是 GEMM 的现实下限**，即最多再省 ~0.9 s；
- **FA 是唯一大杠杆**：8.85 s 对应 42 TFLOPS/卡（13.5% MFU）。若要 10 s，
  FA 必须降到约 4 s（≈30% MFU）且其余不增。这需要 **FA 内核级工作**（tiling/head 打包/核数），
  而任何改变归约顺序的 tiling 都会改变数值 ⇒ 需用户批准。
