# R145／R146 — 排除两个嫌疑，并用真实形状直接测出 GEMM 差距

上一轮（R143）我撤回了"staging 停顿"的解释，并提出"权重物化开销"是主嫌疑。
本轮先测 hook 自身开销（R145），再用**真实形状**直接测独立 GEMM（R146），把嫌疑逐个排除。

## 1. R145：hook 自身开销只有 0.27%，物化假设也被排除

纯 host 计时（perf_counter，forward 内零同步），4 步 × 50 块 = 200 次 block：

| 项 | 每次调用 | 总时长 (200 次) |
|---|---|---|
| `prefetch_layer`（发起异步拷贝 + 重绑下一块张量） | **0.94 ms** | 189.6 ms |
| `pre_forward` | 0.71 ms | 141.5 ms |
| `offload_layer` | 0.57 ms | 113.7 ms |
| `post_forward` | 0.58 ms | 116.3 ms |
| **hook 合计占 block 时间** | **0.27%** | — |

step 18.047 s（与 R143 的 18.076 s 一致）。
**结论：offloader 的 host 开销可忽略（每块合计约 2.8 ms），"物化开销"不是那 3× 的来源。**

## 2. R146：真实形状下的独立 GEMM（不再用缩放估计）

R142/R143 里我用"按 FLOP 比例缩放"来估计真实形状的独立耗时——那对 `torch.mm` **不成立**
（形状变化会改变分块与效率）。本轮直接测 R144 实测出的真实形状：

| case | M×K×N | 独立（裸 `torch.mm`） | 达成 | in-model（R141） | 差距 | 是否含 FP32 guard |
|---|---|---|---|---|---|---|
| `qkv_proj_true` | 10448×5376×10752 | 12.466 ms | 96.9 TF (31.3%) | 41.74 ms | **3.35×** | 否 |
| `mlp_fc1_true` | 10448×5376×14336 | 19.037 ms | 84.6 TF (27.3%) | 54.6 ms | **2.87×** | 否 |
| `attn_out_proj_true` | 10448×3584×5376 | 2.734 ms | 147.3 TF (47.5%) | 19.02 ms | **6.96×** | 是 |
| `mlp_fc2_true_fp32_input` | 10448×7168×5376 | 12.213 ms | 65.9 TF (21.3%) | 30.3 ms | **2.48×** | 是 |

每层合计：in-model 145.66 ms vs 独立 46.45 ms
→ **潜在 4.961 s/step**（若 in-model 达到裸 GEMM 速率）。

**重要限定**：独立的数字是**裸 `torch.mm`**；模型里 `out_proj`/`fc2` 还额外跑
`_MiniMaxH3HalfInputFP32OutputLinearMethod` 的 FP32 范围保护，其 prologue 含
**主机同步**（`float(peak)`）。所以这两项的 6.96×/2.48× **不能全算作 GEMM 差距**。
顺带：`attn_out_proj` 裸 GEMM 反而最快（147.3 TF、47.5% peak），说明小 K 的形状本身不差。

## 3. 三个嫌疑的处置

| 嫌疑 | 状态 | 依据 |
|---|---|---|
| 拷贝停顿 | **已排除** | R143：拷贝在下一个块开始前 22–34 ms 完成 |
| hook 物化 / host 开销 | **已排除** | R145：hook 占 block 时间 0.27% |
| FP32 范围保护的 prologue（含主机同步） | **部分解释 out_proj/fc2**，未单独测出 | 需按 R142 的思路拆分，但整张量 amax 在该 build 上抛 `ReduceMax` |
| **其余（qkv 3.35×、fc1 2.87×）** | **未解释** | 两者都不含 guard；每层仍有 29–36 ms 无法归因，需要 op 级 profiling |

## 4. 下一步（仍为纯测量）

1. 用 op 级 profiler（而非区域计时）看 qkv/fc1 在那 29–36 ms 里执行了什么算子；
   重点怀疑：每 op dispatch/dispatch queue 深度、以及 GEMM 与 concurrent copy 的相互干扰；
2. 单独测 FP32 range guard 的 prologue 成本（换更小的整张量归约或分块 amax 规避 `ReduceMax`）；
3. 只有在 1–2 定位后才谈候选，**任何候选仍按用户判据逐项批准**。

## 限制

- in-model 数字来自 R141，含区域 hook 的同步开销（整步 +2.72 s，分摊到各区域约 5 ms/次）；
  该开销会让差距略偏大，但不改变量级。
- 区域计时是 coarse 归因；310 TF 为数量级假设。
- 本轮未改数学、未改生命周期、未安装候选，**不构成任何数值批准**。
