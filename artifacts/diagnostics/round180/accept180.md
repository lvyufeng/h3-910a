# R180 — 统计内核的验收协议（离线撰写，主机恢复后即可执行）

## 为什么需要它

阶段 A 的价值已被实测标定为 **2.52 s/步**（R178），但那是"一趟归约"的代理数字。
内核一旦能跑，必须立刻回答三个问题：

1. **判定是否等价** —— 与原生的位模式计数给出的判定完全一致吗？
2. **单次耗时是多少** —— 能否接近代理的 3.9/2.9/0.15 ms？
3. **每步真实节省多少** —— 是 2.5 s、1.3 s，还是更少？

没有这三条，2.52 s 就只是一个假设。

## 内核语义（已实现，`round174/src/h3_range_stats.cpp`）

每核归约自己那段切片的**幅度位最大值** `maxMag = max(bits & 0x7fff)`，写入 `y[coreIdx]`。主机取 max 后：

| 条件 | 含义 |
|---|---|
| `maxMag >= 0x7c00` | 存在 NaN 或 Inf |
| `maxMag == 0x7bff` | 存在 \|x\| == 65504（65504 是 FP16 最大有限幅值） |
| 其他 | 全部有限且未饱和 |

只用位模式，**不使用浮点判据**——R165 已实测本设备 `isnan`/`isfinite`/`x!=x`/`max` 都会漏 NaN。

**注意语义边界（必须诚实记录）**：本内核给出的是**判定**（有/无），不是**精确计数**。
R164 已确定审计只消费判定（strict 模式抛错、deferred 模式求 any），所以判定等价即为充分。
若将来需要精确计数，得再加一趟 compare+sum。

## 验收用例（沿用 R166/R167 的既有证据集）

### A. 对抗用例（37 个，与 R166 完全相同，便于直接对照）

必须覆盖：

| 类别 | 用例 |
|---|---|
| 全有限 | 普通正态值；次正规值；全零；±0 |
| 单个非有限 | 一个 NaN；一个 +Inf；一个 -Inf |
| 单个饱和 | 一个 +65504；一个 -65504 |
| 重复饱和 | 多个 +65504；多个 -65504；正负各一 |
| **混合（关键）** | **NaN + 65504**；**Inf + (-65504)**；NaN+Inf+-Inf+±65504 混合 |
| 边界邻域 | 65503；65504-32；最大有限值附近 |
| 形状 | (1,2)、(1,17)、(1,64)、(1,1024)、(55,5376)、(2048,3584)、**(10448,14336)** |

**混合用例是重点**：R164 里正是"NaN + 65504"打穿了基于浮点判据的实现（报 [0,0] 而原生报 [1,1]）。
本内核必须在这类用例上与原生一致。

### B. 真实张量（465 次调用，与 R167 相同口径）

在真实 step 内对 155 个被审张量（3 次前向 × 155）逐条比对判定。

### C. 计时

对三种真实形状各测 warmup 3 / repeats 10 的中位耗时，与 R178 代理值对比：

| 形状 | R178 代理 |
|---|---|
| (10448,14336) | 3.905 ms |
| (10448,10752) | 2.947 ms |
| (3,96768) | 0.146 ms |

## 判定标准（事先写明，避免事后解释）

| 项 | 通过条件 |
|---|---|
| A 对抗 | **37/37 判定一致**，任一不一致即 FAIL |
| B 真实 | **465/465 判定一致** |
| C 计时 | 记录实测值；即使慢于代理也**如实记录**，不调参掩盖 |
| 综合 | A+B 必须全过；C 只报数字 |

**任一判定不一致 = 不可用**，不允许以"差异很小"为由放行（R164 的教训）。

## 预期结论的三种情形

| 内核实测 | 结论 |
|---|---|
| ≤0.5 s/步 | 阶段 A 成立，节省 ≥2.37 s，值得做 op 化与集成 |
| 0.5–1.5 s/步 | 部分成立，节省 1.4–2.4 s，需权衡工程成本 |
| >1.5 s/步 | 不如代理预期，优先转 FA（阶段 C，上界 4.38 s） |

## 附：自检时发现的一个真实陷阱（R180）

`65503.0` 在 float16 里**会舍入成 65504**——最大有限幅值附近的可表示间距是 32
（`2^15 × 2^-10`），所以 65504 之下紧邻的值是 **65472**，而 65503 会被舍入到 65504 本身。

因此"略低于最大、不饱和"的用例**必须用 65472.0**；用 65503 会误判为饱和。
反过来，`65503.0` 是一个很好的"验证舍入"用例，期望判定就是**饱和**。

两例都已写进 `reference180.py`：

| 用例 | 值 | 位模式 | 期望 |
|---|---|---|---|
| `just_below_max` | ±65472 | 0x7BFE / 0xFBFE | 非饱和 |
| `rounds_up_to_max` | ±65503 | **0x7BFF / 0xFBFF** | **饱和** |

这个陷阱在写测试时自己抓到了（自检报出 `just_below_max` 失败），已修正期望值并加了位模式硬断言。
