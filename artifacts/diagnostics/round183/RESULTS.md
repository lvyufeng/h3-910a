# R183 — 阶段 A **双轴通过**：15/15 判定正确 + 2.68 s/步

## 一、修掉的两个真 bug

### bug 1：写回越界（R182 判定垃圾的根因）

R182 的写法：`SetGlobalBuffer(y + coreIdx, 1)` 却 `DataCopy(yGm_, oc, 8)`——
**每核写 8 个 int，偏移只有 coreIdx**，8 核互相覆盖，且 `oc` 里只有第 0 个是真实值、其余是未初始化垃圾。

哨兵探针（输出预填 `0xDEADBEEF`）给出了决定性证据：

```
修复前: [0]=0x3c00 [1]=0 [2]=0 [3]=0x3c00 [4]=0x334dbabe [6]=0xbca2407f [7]=0x4036b568
修复后: [0]=0x3c00 [1..7]=0
```

修法：**每核独占一个 8-int（32 字节）对齐区间**，先全部置 0 再把 blockMax 放进 slot 0；
主机取全部 64 个槽的最大值。输出形状相应改为 `coreNum × 8 = 64`。

### bug 2：长度未对齐（小张量读出常数）

小张量（2–6 元素）时所有用例都返回同一个 `0x5209`——`DataCopy`/`ReduceMax` 要求长度按
32 字节对齐，2 个 half 才 4 字节，读到的是垃圾。

对齐到 128 元素倍数后立刻全部正确。**注意：补零用的是 `0x0000`（+0.0），幅值位为 0，
不影响最大值**，所以判定语义不变。真实审计张量都远大于此。

### 关键结论：**AscendC 的 `ReduceMax` 会传播 NaN**

`single_nan` 返回 **0x7e00**（NaN 的位模式），说明归约没有被 NaN 吃掉。

这一条纠正了我此前的担心：R165 测的是 **torch 的 `max()`**（确实会掩掉 NaN），
但**AscendC 的 `ReduceMax` 原语行为不同**——所以 `Abs + ReduceMax` 这个最简方案能正确工作。
这也解释了为什么不需要 `Ands` 位掩码、不需要 `Compare` 组合。

## 四、测试代码里的一个坑（记录以免重犯）

我手写的 C++ `f16()` 转换是**截断**而非 IEEE 就近舍入：
65503 距 65472 是 31、距 65504 只有 1，正确应得 `0x7bff`，但我的辅助函数给了 `0x7bfe`。

**是测试期望值错了，不是内核错了。** 已改成显式位模式 `0x7bff/0xfbff` 钉住，
与 `round180/reference180.py`（`struct.pack`，舍入正确）一致。
