# R273 — 对 A3 的再分析：重排**本身**可能不够，真正的锁是共享 UB 缓冲上的自动同步

## 一、重新审视指令顺序

当前每块（`compute_in_each_kv_block` 结尾 + 下一块开头）：

```
[softmax_j (向量)] [S_{j+1} (cube)] [PV_j (cube)] || 下一块 [softmax_{j+1} (向量)] ...
```

`PV_j` 与 `softmax_{j+1}` 在指令流上**已经是相邻且互相独立**的
（PV 依赖 P_j 与 V_j；softmax_{j+1} 依赖 S_{j+1}）——理论上硬件/编译器**已经可以**让它们重叠。

## 二、那为什么 mac_ratio 只有 22.7%？

两个更可能的锁：

1. **自动同步插入在共享 UB 缓冲上**：`Pij_l1_zN`（L1）与 `Oij_ub_zN`/`Oi_ub_zN`（UB）
   在相邻迭代间复用，TIK 的 auto-sync 会保守地在调用边界插入 wait，
   把本可重叠的 PV 与 softmax 串起来；
2. **UB 容量决定了无法双缓冲**：R272 实测 UB 只剩 29 KB，连一份 `Oi_ub_zN`(64 KB) 都不够
   ⇒ 想给 `Pij`/`Oij` 做双缓冲在 64 KB 级 tile 下根本放不下。

## 三、结论：想重叠，必须先**降低 UB 占用**

而不是简单重排（A3）。可行路径按代价排序：

| 路径 | 做法 | 代价 |
|---|---|---|
| **U1（推荐）** | 把 `Oi` 重做为 **L1 常驻 + 分块累加**（现在 `Oij_ub_zN` 在 UB 里做临时累加），腾出 UB 给 `Pij` 双缓冲 | 中，需改 `output_update`/`output_compute` 的缓冲位置 |
| U2 | 缩小 `Br`（向量 tile）使 `Oi_ub_zN` 从 64 KB 降到 32 KB | 小，但会降低 cube 复用率，可能整体变慢 |
| U3 | 手工在关键边界**移除 auto-sync** 并加显式 flag | 高（易错、可能数据竞争） |
| U4 | 放弃 UB 双缓冲，改 AscendC 重写（对 UB/L1 有完全控制） | 最高（周级） |

## 四、与 15 s 目标的关系

- 若 U1 成功：cube 与 vector 重叠 30–40%，FA 152→约 105–115 ms，**足以跨过 15 s**；
- 若 U1 失败或收益 <10%：15 s 不可达（在现有数值约束下），应回到 16.32 s 交付并向用户说明；
- 10 s 的判断不受影响（R280 已定档：需 FA ~2.2× 且非 FA −3.7 s）。

## 五、下一步（R274）

   确认 `Oi` 能否全程放 L1（`Oi_l1_zN` 已存在，关键是 `Oij_ub_zN` 的临时作用）；
2. 评估 U1 的 UB 释放量（需 ≥2×S 缓冲：约 76–150 KB）；
3. 若可行 → 按 U1 改私有副本 → 走 R267 回路测 ms + 四项数值。
