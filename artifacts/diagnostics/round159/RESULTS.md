# R159 — FA 只读分析：撤回一个错误的怀疑，并找到一个量化且可能免费的 ~0.64 s

本轮**不用机器**，只读源码 + 仓库里已有的运行日志。

## 1. 撤回：我差点提一个无价值的候选

读 `pick_tile()`：

```python
"""Largest multiple of align that is <= cap and divides n exactly."""
br = pick_tile(n, 128); bc = pick_tile(n, 304)
```

因为 **41792 = 64 × 653（653 为素数）**，能整除且 ≥16 的只有 16/32/64，
我一度判定"FA 被迫用 64×64 小 tile"。

**这是错的。** `_kernel_sequence_length()` 会补齐：
`quantum = lcm(128,304) = 2432`，`padded = ceil(41792/2432)×2432 = 43776`（+4.75%，未超其 10% 上限），
于是 `pick_tile(43776,128)=128`、`pick_tile(43776,304)=304`。

**仓库里的运行日志实证**：

```
[FA910A] plan input_N=41792 kernel_N=43776 key_limit=41769 original_pad=23
core_budget=30 blockDim=30 B=1 H=7 N=43776 D=128 Br=128 Bc=304
```

即 kernel 实际是 **Br=128 / Bc=304 / 30 核**，本来就是大 tile。该怀疑**在提出前撤回**。

## 2. 真实且可量化的浪费：补齐带来的 9.72%

| 项 | 值 |
|---|---|
| 输入 N | 41792 |
| kernel N（补齐后） | **43776**（+1984 行，+4.75%） |
| 因二次复杂度放大的无用 FLOPs | **+9.72%** |
| 当前 tile 数 | 49,248 |
| 同 tile 形状下不补齐的 tile 数 | 45,126（**−8.37%**） |

## 3. 达成效率

| 项 | 值 |
|---|---|
| 有用 FLOPs | 313 TFLOP/rank/step |
| 耗时 | 7.607 s |
| 有用达成 | **41.1 TFLOPS/卡** |
| 含补齐的硬件达成 | 45.1 TFLOPS/卡（约为 310 假设峰的 14.6%） |

## 4. 候选（**需要你批准**）

**不补齐，直接用 N=41792 + Br=128 + Bc=304 启动同一个 CANN kernel。**

**为什么应当数值恒等**：
- 补齐的 key 行是**零值**且被 `key_limit=41769` **掩掉**，不产生任何真实贡献；
- 补齐的 query 行算出的输出**被丢弃**；
- flash attention 的**行块彼此独立**，每行对 304 宽 key 块的累加顺序**不变**。

**预期收益**：**≈ 0.74 s/步**（−8.37% tile）。

**实现代价**：`_kernel_sequence_length` 里一处条件改动即可；然后用与 R148 相同的方式
（进程内两条路径都算、仍返回原生结果）做**逐位比较**。

**风险**：中等——它会走到 padding 目前刻意避开的**尾块路径**，正确性与速度都必须实测。

## 5. 这不能解决什么

它**不能**把 41 TFLOPS 提到 10 s 路径所需的约 69 TFLOPS。CANN kernel 的 softmax / cube 效率仍需
**新内核工作**，那才是 #5 的主体，且需要你的决定。

## 结论

FA 的启动计划在我能检查的轴（Br/Bc/核数/重划分）上**已经调优**（代码里还记录了 558→317 ms 的重划分收益）。
唯一明确、可量化、可能免费的项是**补齐的 9.72%**，约 **0.74 s/步**。
